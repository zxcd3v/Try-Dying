# Аудиомодем

Передача файла между двумя ноутбуками **только через звук**: динамик одного
играет, микрофон другого слушает. Ни сети, ни кабелей. Приёмник сам
доказывает результат — сверяет SHA-256 и печатает вердикт.

Хакатон Nuclear IT Hack School, «Аудиомодем XXI века».

| | |
|---|---|
| **Что умеет** | передать любой файл звуком, починить битые байты, добрать потерянные кадры, подтвердить SHA-256 |
| **Три профиля** | `robust` — до −9 дБ SNR (шум громче сигнала), `medium` — 97.5 Б/с, `fast` — 308 Б/с в тишине |
| **Адаптация к залу** | зонд перед передачей меряет SNR всех полос одним FFT и выбирает лучшую |
| **Проверено** | 133 автотеста, таблица из 60 передач на канал-симуляторе |
| **Документация** | [Архитектура](docs/ARCHITECTURE.md) · [Протокол](docs/PROTOCOL.md) · [Ограничения](docs/LIMITATIONS.md) · [Тесты и результаты](docs/TEST_RESULTS.md) |

## Установка

Python 3.11+ (разрабатывалось на Windows 11):

```
pip install numpy scipy sounddevice reedsolo pytest matplotlib
```

Русский вывод на Windows требует `PYTHONUTF8=1` — иначе консоль упадёт с
`UnicodeEncodeError`. В PowerShell это `$env:PYTHONUTF8=1` один раз на сессию.

## Быстрый старт без звука (30 секунд)

Демо на одной машине: блоки ходят файлами через общий каталог-линк, а
протокол работает ровно тот же. Два терминала, **приёмник запускается
первым**:

```
PYTHONUTF8=1 python recv.py --mode medium
PYTHONUTF8=1 python send.py file.txt --mode medium
```

Ожидаемый результат:

```
приёмник:     УСПЕХ: SHA-256 совпал — file.txt (220 Б) за 3.1 с
              Файл: received\file.txt
отправитель:  УСПЕХ: приёмник подтвердил DONE (SHA-256 сошёлся)
```

Показать, как решение переживает помехи (Reed-Solomon чинит биты, NACK-цикл
добирает потерянные кадры) — те же команды с флагами у отправителя:

```
PYTHONUTF8=1 python send.py file.txt --mode medium --bit-flip 0.002 --block-loss 0.1
```

## Живое демо через звук

Те же команды с флагом `--audio` на **обеих** сторонах — слой протокола не
меняется, меняется только транспорт:

```
PYTHONUTF8=1 python recv.py --audio            # принимающий ноутбук, первым
PYTHONUTF8=1 python send.py файл.bin --audio   # передающий
```

### Обязательная подготовка (без неё передача не пойдёт)

1. **Отключить «улучшения звука» Windows** на обоих ноутбуках: Параметры →
   Система → Звук → свойства микрофона → Дополнительно → снять
   «Аудиоулучшения»; то же самое у динамиков. AGC и шумоподавление
   уничтожают MFSK-тона — это главная причина неудач.
2. **Не брать виртуальные устройства с обработкой** (например, ASUS «AI
   Noise-cancelling Input/Output»). Выбирать сырые `Microphone Array` /
   `Speakers`; явный выбор — `--in-device` / `--out-device` (номер или
   подстрока имени из
   `python -c "import sounddevice; print(sounddevice.query_devices())"`).
3. **Громкость** воспроизведения 70–80 %, микрофон ~80 %, без усиления (boost).
4. **Расстояние** 30–50 см (для `fast` — 20–40 см), ноутбуки «лицом» друг к другу.

### Чек-лист живого прогона

1. Оба ноутбука в розетке, «улучшения звука» выключены.
2. Прогнать АЧХ-свип (см. ниже), убедиться, что полоса профиля не в провале.
3. Приёмник: `python recv.py --audio`, затем отправитель:
   `python send.py файл.bin --audio` (файл ≥ 1 КБ, профиль robust).
4. Обе стороны печатают `УСПЕХ` — повторить 3 раза подряд.
5. Показать NACK по воздуху: во время партии на секунду прикрыть микрофон
   ладонью — повтор доберёт битые кадры (у отправителя вырастет «повторно»).
6. Страховочное видео успешной передачи записать и хранить **вне** рабочего
   каталога (телефон или облако).

### Профиль побыстрее

```
python recv.py --audio --mode medium     # и то же на отправителе
python recv.py --audio --mode fast       # тишина, дистанция 20–40 см
```

Служебные кадры (HEADER/NACK/DONE) всегда остаются в robust — приёмник
слушает обе сетки. Если канал не держит выбранный профиль, `send.py` сам
советует перезапуститься живучее (`СОВЕТ: канал плохо держит…`).

## Настройка: каталог `config/`

Ни один путь не зашит в код. Значения по умолчанию CLI берёт из
[`config/audiomodem.env`](config/audiomodem.env) (образец со всеми ключами и
пояснениями — [`config/example.env`](config/example.env)); флаги командной
строки перекрывают файл.

| Ключ | Что задаёт | По умолчанию |
|---|---|---|
| `MODE` | профиль передачи данных | `robust` |
| `LINK_DIR` | каталог спул-модема, общий для обеих сторон | `link` |
| `OUTPUT_DIRECTORY` | куда приёмник кладёт принятый файл | `received` |
| `TIMEOUT_S` | сколько ждать другую сторону, секунды | `120` |
| `IN_DEVICE` / `OUT_DEVICE` | устройства sounddevice для `--audio` | системные |

Порядок поиска конфига: `$AUDIOMODEM_CONFIG` → `config/audiomodem.env` →
`config/example.env`. Свой файл для конкретного стенда:

```
AUDIOMODEM_CONFIG=config/demo.env python recv.py --audio
```

Ошибка в конфиге (неизвестный профиль, нечисловой таймаут) — понятное
сообщение и выход с кодом 2 ещё до начала передачи.

### Флаги обеих команд

| Флаг | Значение |
|---|---|
| `--mode robust\|medium\|fast` | профиль передачи данных |
| `--audio` | живой звук вместо спул-каталога |
| `--link DIR` | каталог спул-модема (без `--audio`) |
| `--out DIR` | куда положить принятый файл (только `recv.py`) |
| `--timeout СЕК` | сколько ждать другую сторону |
| `--in-device` / `--out-device` | устройства sounddevice |
| `--bit-flip P` / `--block-loss P` / `--seed N` | демо помех (только спул) |

## Архитектура и протокол — коротко

Два слоя с жёсткой границей (контракт v1.2):

```
файл → zlib → кадр (CRC32) → Reed-Solomon → блок → MFSK-символы → звук
звук → FFT → символы → блок → Reed-Solomon → CRC32 → кадр → сборка → SHA-256
```

- **Модем** — «глупая труба»: блок байтов ↔ звук. MFSK (номер тона несёт
  биты), демодуляция FFT по окну символа, каждый аир-кадр самодостаточен —
  своя chirp-преамбула и заголовок с длиной.
- **Протокол** — сжатие, кадрирование, Reed-Solomon, NACK-цикл, SHA-256.
  Отправитель шлёт партию кадров подряд; приёмник отвечает одним NACK со
  списком недостающих либо DONE.

Ответы на вопросы «почему так»:

- **Почему MFSK, а не PSK/QAM?** Амплитуда гуляет от расстояния и AGC, фазу
  рушат эхо и дрейф часов. Пик частоты в FFT виден сквозь шум и не сдвигается
  эхом ([ADR-0001](docs/adr/0001-mfsk-modulation.md)).
- **Почему NACK партиями, а не подтверждение каждого кадра?** Каждый разворот
  «динамик↔микрофон» стоит 0.5–1 с: stop-and-wait упирается в ~150–250 Б/с
  даже в тишине ([ADR-0002](docs/adr/0002-batch-nack-and-self-contained-frames.md)).
- **Почему такие частоты?** Ниже 1.5 кГц — голос и гул зала, выше ~10 кГц
  дешёвые тракты заваливают АЧХ. Внутри окна 1.5–9.5 кГц каждый тон кратен
  ширине FFT-бина, иначе энергия размазывается по соседям
  ([ADR-0003](docs/adr/0003-adaptive-band-calibration.md)).
- **Почему fast именно 9 × 4-MFSK?** У одиночного MFSK скорость ~`W·b/2^b`,
  максимум при b ≤ 2; вверх — только параллельные тона
  ([ADR-0004](docs/adr/0004-fast-parallel-subcarriers.md)).

Подробно: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) и
[docs/PROTOCOL.md](docs/PROTOCOL.md).

## Профили и пороги

Пороги сняты на канал-симуляторе (`modem/channel.py`, петля tx → канал → rx)
и закреплены регрессионными тестами; скорость — байты партии, делённые на
длительность сигнала со всеми преамбулами и паузами.

| Профиль | Канал | SNR уверенного приёма | Скорость (модем) |
|---|---|---|---|
| robust (4-MFSK) | белый шум поверх тихого сигнала | **−9 дБ** | 16.9 Б/с |
| robust (4-MFSK) | шум + дрейф часов ±0.1 % + эхо 50 мс | **−6 дБ** | 16.9 Б/с |
| medium (16-MFSK) | оба канала | **−3 дБ** | 97.5 Б/с (5.8× robust) |
| fast (9 × 4-MFSK) | белый шум поверх тихого сигнала | **+12 дБ** | 308 Б/с (3.2× medium) |
| fast (9 × 4-MFSK) | шум + дрейф часов ±0.1 % + эхо 50 мс | **+21 дБ** | 308 Б/с |

Отрицательный порог означает, что шум **громче** сигнала: при −9 дБ — в
8 раз. Fast — профиль тишины: аккорд несёт 18 бит на 9 поднесущих, но
амплитуда делится на всех, каждый тон в 9 раз тише — отсюда мягкие пороги.
Заявленные в задании 2–5 КБ/с некогерентным MFSK в окне 1.5–9.5 кГц
физически недостижимы (предел ~500 Б/с) — зафиксирован честный темп.

Ниже порога партия деградирует предсказуемо: кадры теряются целиком или
приходят с точечными битовыми ошибками, но байты никогда не съезжают. На это
и опирается протокол: Reed-Solomon чинит биты, NACK добирает погибшие кадры.

## Адаптивная полоса: калибровка перед передачей

АЧХ связки «динамик → комната → микрофон» имеет провалы в заранее
неизвестных местах. Чтобы не попасть в провал, `--audio` перед данными сам
проводит калибровку — добавлять ничего не нужно:

1. отправитель играет **зонд** (~0.5 с широкополосного мультитона);
2. приёмник **одним FFT** меряет SNR всех полос сразу и шлёт лучшую
   служебным кадром в robust;
3. отправитель объявляет решение обратно, обе стороны переходят на полосу.

| Профиль | Полосы (жирная — по умолчанию) |
|---|---|
| medium | 1500–6000 / **2400–6900** / 3600–8100 / 4800–9300 Гц |
| fast | 1600–8600 / **2000–9000** / 2200–9200 / 2400–9400 Гц |
| robust | 4500–6900 Гц — якорная, не двигается никогда |

Обе стороны печатают итог:

```
Полоса: 4800–9300 Гц — полосу выбрал приёмник по зонду
SNR по полосам: 1500–6000 Гц +17 дБ, 2400–6900 Гц +23 дБ, 3600–8100 Гц +32 дБ, 4800–9300 Гц +39 дБ
```

Служебные кадры от калибровки не зависят — они всегда в robust на якорной
полосе, поэтому сорвавшееся рукопожатие не ломает передачу: работаем на
полосе по умолчанию, сеанс теряет пару секунд. На спул-линке калибровки нет
вовсе — блоки ходят файлами, спектра в канале не существует.

## Диагностика тракта

### АЧХ перед первой передачей

```
python tools/afr_sweep.py record   # на принимающем, первым
python tools/afr_sweep.py play     # на передающем
python tools/afr_sweep.py both     # один ноутбук сам играет и пишет
```

`record`/`both` сохраняют `out/afr.wav` и `out/afr.png` и печатают уровень
полосы каждого профиля относительно медианы свипа. Провал глубже ~15–20 дБ —
повод сдвинуть частоты профиля. Если запись нулевая: проверить приватность
микрофона Windows и взять WASAPI-устройство (`--in-device`); для `both` вход
и выход должны быть одного host API.

### Если fast «слышно, но не декодится»

Каждый тон аккорда в 9 раз тише одиночного, поэтому провал АЧХ способен
убить целую поднесущую, а её 2 битые бита в каждом символе валят
Reed-Solomon всего кадра. Зонд играет известную последовательность аккордов и
печатает по каждой поднесущей ошибки, отрыв тона и фон:

```
python tools/fast_probe.py record   # на принимающем, первым
python tools/fast_probe.py play     # на передающем
python tools/fast_probe.py analyze  # пересчитать из out/fast_probe.wav
```

Читать так: «МЕРТВА/слаба» + тихий «Тон» — провал АЧХ на этой полосе
(сверить с `out/afr.png`); ошибки размазаны ровно по всем поднесущим при
высоком «Фоне» — интермодуляция динамика (убавить громкость, увеличить
дистанцию); в упор (10–15 см) не лечится — виноват тракт, а не шум комнаты.

Прочие инструменты: `tools/mic_meter.py` (жив ли вход),
`tools/speaker_test.py` (тоны и преамбула на выход), `tools/make_wav.py`
(WAV и спектрограмма в `out/` для доклада).

## Ограничения

Коротко (полностью — [docs/LIMITATIONS.md](docs/LIMITATIONS.md)):

- скорость ограничена модуляцией: потолок некогерентного MFSK в окне
  1.5–9.5 кГц ~500 Б/с, у нас 308 Б/с в fast;
- fast требует тишины и дистанции 20–40 см;
- имя файла — **до 14 байт UTF-8** (HEADER обязан влезть в один блок robust);
- один файл за сеанс, полудуплекс, без докачки после прерывания;
- профиль не меняется на лету — только перезапуск обеих сторон;
- шифрования нет: акустический канал слышит вся комната, SHA-256 доказывает
  целостность, но не конфиденциальность;
- аудиоулучшения Windows убивают тона — это настройка системы, а не код;
- живые прогоны `--audio` для тикетов 07/09/10 проведены не полностью,
  строк «воздух» в таблице результатов пока нет.
