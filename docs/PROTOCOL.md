# Спецификация акустического протокола

Версия контракта между слоями — **v1.2**. Термины — [CONTEXT.md](../CONTEXT.md),
обоснования — [docs/adr/](adr/), обзор слоёв — [ARCHITECTURE.md](ARCHITECTURE.md).

## Цели

1. Передать произвольный файл динамик → микрофон между двумя ноутбуками и
   **доказать** совпадение содержимого (SHA-256).
2. Пережить реальный канал: шум зала, эхо, провалы АЧХ, расхождение часов
   звуковых карт до ±0.1 %.
3. Дать выбор «надёжность ↔ скорость» тремя профилями без смены модуляции.
4. Деградировать предсказуемо: канал хуже — передача дольше, но не
   искажает данные молча.

Не цели: скрытность, шифрование, полный дуплекс, передача нескольких файлов
за сеанс (см. [LIMITATIONS.md](LIMITATIONS.md)).

## Физический уровень

- Дискретизация **48 000 Гц**, моно, float32.
- Рабочее окно **1.5–9.5 кГц** (ниже — голос и гул зала, выше — завал АЧХ
  дешёвых трактов).
- Модуляция **MFSK**: в каждом символе звучит один тон из сетки профиля
  (в fast — аккорд из 9 тонов). Значение символа = номер тона.
- Демодуляция: FFT по окну символа, argmax по бинам сетки. Каждый тон
  кратен ширине бина `SAMPLE_RATE / symbol_samples` — иначе энергия
  размазывается по соседям.
- Амплитуда 0.8 пиковой, плавные фронты (ramp) против щелчков.

| Профиль | Тоны | Сетка по умолчанию | Символ + защитный интервал | Бит/символ | Блок, Б | Скорость модема |
|---|---|---|---|---|---|---|
| robust | 4 | 4500–6900 Гц, шаг 800 Гц | 12.5 мс | 2 | 96 | 16.9 Б/с |
| medium | 16 | 2400–6900 Гц, шаг 300 Гц | 4.17 мс | 4 | 128 | 97.5 Б/с |
| fast | 36 (9 × 4) | 2000–9000 Гц, шаг 200 Гц | 5.83 мс | 18 | 255 | 308 Б/с |

Скорость модема — байты партии, делённые на длительность сигнала со всеми
преамбулами и паузами; она закреплена тестами в `tests/test_tx.py`.

**Полоса** (ADR-0003) — позиция сетки тонов внутри окна, смещение кратно
FFT-бину профиля:

| Профиль | Полосы (жирная — по умолчанию) |
|---|---|
| medium | 1500–6000 / **2400–6900** / 3600–8100 / 4800–9300 Гц |
| fast | 1600–8600 / **2000–9000** / 2200–9200 / 2400–9400 Гц |
| robust | 4500–6900 Гц — якорная, не двигается никогда |

## Формат передачи

Данные проходят три вложенных формата: файл → протокольный кадр → блок →
аир-кадр.

**1. Протокольный кадр** (то, что для модема — просто содержимое блока):

```
| magic 0xA7 0x55 | type 1 Б | seq 2 Б | total 2 Б | len 2 Б | payload | CRC32 4 Б |
```

Служебные поля — 13 байт. Типы:

| Тип | Код | Payload | Кто шлёт |
|---|---|---|---|
| HEADER | 0x01 | `sha256 (32 Б) + размер файла (4 Б) + профиль (1 Б) + имя UTF-8` | отправитель, ×3 в начале и как пинг |
| DATA | 0x02 | кусок zlib-потока, `seq` — его номер, `total` — сколько всего | отправитель |
| NACK | 0x03 | список недостающих `seq` по 2 байта; `0xFFFF` — «повтори HEADER» | приёмник |
| DONE | 0x04 | пусто | приёмник |
| BAND | 0x05 | номер полосы, 1 байт | обе стороны (калибровка) |

**2. Блок** = кадр, закодированный Reed-Solomon. Паритетных байт на блок:
robust 32 (50 % кадра), medium 26 (≈25 %), fast 32 (≈14 %). Отсюда полезная
ёмкость payload: **robust 51 Б, medium 89 Б, fast 210 Б**. Приёмник не знает
профиль пришедшего блока заранее и пробует каждый вариант паритета — неверно
раскодированное отсекает CRC32.

**3. Аир-кадр** — то, что звучит для одного блока (ADR-0002):

```
chirp-преамбула → тишина → аир-заголовок ×3 → символы данных (+ пилоты) → тишина
```

Аир-заголовок — длина блока (2 байта) + CRC-8, повтор ×3, приём по
большинству. Не сошёлся — весь аир-кадр отбрасывается, его добирает NACK.
Кадр самодостаточен: синхронизируется и декодируется независимо от соседей.

## Установление и завершение передачи

Полудуплекс, инициатива всегда у отправителя. Приёмник запускается первым.

1. **Калибровка** (только `--audio`; на спул-линке спектра не существует и
   фаза пропускается): отправитель играет зонд ~0.5 с → приёмник одним FFT
   меряет SNR всех полос и шлёт лучшую кадром BAND в robust → отправитель
   объявляет решение обратно тем же BAND. Нет подтверждения за
   `CALIBRATION_WAIT_S` (8 с) — обе стороны остаются на полосе по умолчанию.
   Итог печатают обе стороны строкой `Полоса: …`.
2. **Первая партия**: HEADER ×3 (robust, якорная полоса) + все DATA-кадры
   (профиль сеанса, выбранная полоса) подряд, без ожидания подтверждений.
3. **Ответ приёмника** после партии — ровно один: NACK со списком
   недостающих `seq` либо DONE.
4. **Цикл добора**: отправитель шлёт только затребованное NACK'ом; приёмник
   снова отвечает. Повторяется, пока не соберётся файл.
5. **Завершение**: собрав все куски, приёмник распаковывает zlib, сверяет
   SHA-256 и размер, печатает вердикт и шлёт DONE. Отправитель, получив
   DONE, печатает свой вердикт и выходит.
6. **Дослуживание DONE** (тикет 12): приёмник после успеха не уходит сразу,
   а слушает ещё окнами длиннее цикла пинга отправителя (`RESPONSE_WAIT_S`
   = 12 с). Отправитель, не расслышавший DONE, пингует HEADER'ом — приёмник
   отвечает DONE ещё раз. Полная тишина в окне означает, что отправитель
   ушёл.

## Синхронизация

- **Поиск кадра** — нормированная корреляция с chirp-преамбулой. Порог 0.25
  (fast — 0.5) при шумовом фоне корреляции ~0.07.
- **Дрейф часов** — банк шаблонов преамбулы по сетке масштабов времени
  −0.1 %…+0.1 % с шагом 0.05 %: длинный chirp теряет корреляцию уже при
  ~0.05 % расхождения. Дрейф не накапливается между кадрами — каждый кадр
  ресинхронизируется своей преамбулой (ADR-0002).
- **Символьный тайминг внутри кадра** — пилот-символы, известные заранее,
  вставляются каждые `pilot_every` символов данных.
- **Эхо** — защитный интервал после каждого символа; в fast заголовок ещё и
  отодвинут от преамбулы паузой длиннее критерия эха (55 мс), иначе эхо
  полноамплитудной преамбулы давит аккорды, которые в 9 раз тише.
- **Полудуплекс на живом звуке** — своё эхо после проигрывания
  выбрасывается; часы приёма — аудио-время (число разобранных сэмплов);
  партия считается законченной после тишины `quiet_gap_s`.

## Ошибки и восстановление

Четыре рубежа, каждый чинит свой класс ошибок:

| Рубеж | Что ловит | Что делает |
|---|---|---|
| Аир-заголовок ×3 + CRC-8 | искажение длины блока | отбрасывает аир-кадр целиком |
| Reed-Solomon | точечные битовые ошибки внутри блока | **чинит на месте** до `паритет/2` байт |
| CRC32 кадра | то, что RS не спас или починил неверно | отбрасывает кадр |
| SHA-256 + размер файла | любое расхождение с оригиналом | вердикт «не совпал», передача не считается успешной |

Потерянное добирает NACK-цикл: приёмник перечисляет недостающие `seq`,
отправитель шлёт только их. Если HEADER не принят, приёмник не знает даже
общего числа кадров и просит его сентинелом `0xFFFF`. Ответ приёмника,
погибший в канале, не тупик: отправитель через `RESPONSE_WAIT_S` пингует
HEADER'ом, и приёмник отвечает заново.

Ниже порога SNR партия деградирует предсказуемо: кадры либо теряются целиком
(не сошёлся аир-заголовок), либо приходят с точечными битовыми ошибками —
байты никогда не съезжают, длина блока сохраняется. Именно на это опирается
протокол. Когда повторов накапливается больше, чем кадров в файле,
`send.py` советует перезапустить обе стороны на профиле живучее.

Отказы, которые протокол не скрывает, а честно показывает пользователем:
нет ответа `--timeout` секунд (по умолчанию 120) → сообщение «запущен ли
recv.py / слышит ли нас его микрофон» и выход 1; SHA-256 не сошёлся при
всех собранных кадрах → выход 1; Ctrl+C → выход 130.

## Совместимость

- **Контракт v1.2** между слоями: `send_blocks(blocks, profile)`,
  `receive_blocks(profile, timeout_s)`, `PROFILES`, `MAX_BLOCK` плюс
  калибровка. Любая реализация контракта подставляется в протокол без
  правок — этим пользуются три транспорта: живой звук (`AudioEndpoint`),
  спул-модем между процессами (`SpoolEndpoint`) и фейковый модем в одном
  процессе для тестов.
- **Служебные кадры всегда robust на якорной полосе** — канал управления не
  зависит ни от профиля сеанса, ни от результата калибровки.
- **Профиль сеанса объявляется в HEADER** (1 байт), поэтому приёмник, даже
  запущенный с другим `--mode`, узнаёт профиль данных из первого же
  принятого HEADER.
- **Версионирование** — magic `0xA7 0x55` плюс контракт v1.2; кадр с чужим
  magic молча игнорируется, так что посторонний звук не ломает сеанс.

## Пример

Файл `file.txt` (220 Б), профиль medium, спул-линк, помех нет:

```
Отправитель                                  Приёмник
                                             recv.py: слушаю линк link, профиль medium
send.py: Отправка file.txt (220 Б), кадров: 2
   ── BAND (robust) ─────────────────────►   (спул: калибровки нет,
   ◄──────────────── BAND (robust) ───────    полоса по умолчанию)
   Полоса: 2400–6900 Гц                      Полоса: 2400–6900 Гц
   ── HEADER ×3 (robust) ───────────────►    sha256, размер 220, профиль medium, имя
   ── DATA seq=0,1 (medium) ────────────►    кадры собраны, zlib распакован
   ◄──────────────── DONE (robust) ───────   УСПЕХ: SHA-256 совпал — file.txt
   УСПЕХ: приёмник подтвердил DONE           Файл: received\file.txt
```

С помехами между шагами 4 и 5 появляется цикл:

```
   ── DATA seq=0..7 ────────────────────►    кадры 3 и 5 не прошли CRC32
   ◄──────────────── NACK [3,5] ─────────
   ── DATA seq=3,5 ─────────────────────►    файл собран
   ◄──────────────── DONE ───────────────
```

Воспроизвести обе картины можно без звука:

```
PYTHONUTF8=1 python recv.py --mode medium
PYTHONUTF8=1 python send.py file.txt --mode medium --bit-flip 0.002 --block-loss 0.1
```
